[modules] Top-level routine used before its declaration → undeclared identifier
Trap: at module scope Nim resolves symbols top-down — calling proc B from
proc A's body fails with `Error: undeclared identifier: 'B'` when B's
`proc` is written below A in the file (true even for plain non-generic
procs; there is no implicit forward referencing).
Symptom: `undeclared identifier: 'eventName'` / `'PostureClass'` at the
call site, though the symbol exists later in the same module.
Fix: move the callee above every caller (or add a forward declaration
`proc foo*(x: T): R {.forward.}` — reordering is the idiomatic fix).
Snippet:
  proc eventName*(k: EventKind): string = ...   # must come FIRST
  proc eventToJson*(e: Event): JsonNode =
    result["kind"] = %(eventName(e.kind))       # now resolves
(Nim 2.2.4, observed 2026-10-01.)

[idiom] `@[]` literals in a call to an openArray[T]/typed param → type
mismatch "seq[empty]"
Trap: passing bare `@[]` for a `seq[WindLineSlot]`/typed parameter makes
the literal infer `seq[empty]` and the call fails with
`Error: type mismatch ... [1] @[]: seq[empty]` (the element type cannot
propagate INTO the literal from an overloaded proc's params).
Symptom: the "Expected one of" block lists the right overload with the
literal slot mismatched at its position.
Fix: bind an explicitly-typed empty first (`var wsl: seq[WindLineSlot]`
then pass `wsl`), or write `@[].seq[WindLineSlot]`.
(Nim 2.2.4, observed 2026-10-01; test-side call, one compile cycle.)

[proc-const-array] A `const` array literal inside a proc that references a
PROC PARAMETER fails with: `Error: cannot evaluate at compile time:
distKm`. Seen on Nim 2.2.4 building a fixture Route:
`const w = [WeatherPoint(distKm: distKm, ...)]` inside
`proc flatRoute(distKm: float)` — the literal looks static but binds the
runtime param. Fix: `let w = [...]` (or hoist the constant out). Cousin of
the implicit-result/no-defaults class: anything spelled `const` is a
compile-time demand on every referenced name.
