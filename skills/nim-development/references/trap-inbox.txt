[footgun] No `isFinite` for floats in `std/math` (Nim 2.2.4)
  Reaching for `x.isFinite` (habit from other languages) does not compile:
  `Error: undeclared field: 'isFinite' for type system.float64`.
  Gate on `classify` instead:
    func finite(x: float64): bool {.inline.} =
      classify(x) in {fcNormal, fcSubnormal, fcZero, fcNegZero}

[cli] `nim check` accepts only one file per invocation (Nim 2.2.4)
  Batch-style checking a project — `nim check --styleCheck:error src/a.nim
  src/b.nim` — fails with an error that misleads toward a `--run` problem:
  `Error: arguments can only be given if the '--run' option is selected`.
  The actual cause is the argument count. Check one file per invocation,
  or check an entry module that imports the rest of the project.

[parsecsv] `CsvParser.open` string overload raises CsvError on a missing
file; the stream overload asserts on nil (Nim 2.2.4)
  Opening via `p.open(newFileStream(f, fmRead), f)` crashes when the file
  is missing, because `newFileStream` returns nil instead of raising:
  `Error: unhandled exception: lexbase.nim(141, 9) 'input != nil'`.
  Use the string overload instead — a missing file then raises
  `CsvError: Error: cannot open: <path>` (CsvError is `object of IOError`),
  so one `except IOError` handler covers it and the message names the path:
    var p: CsvParser
    p.open(path)          # missing file -> CsvError "cannot open: <path>"
    p.readHeaderRow()
    while p.readRow(): discard p.rowEntry("col")  # header-keyed access

[sequtils] `mapIt` takes an expression over `it`, not a lambda (Nim 2.2.4)
  Writing `toSeq(0..<n).mapIt(_ => 300.0)` (JS/Python muscle memory) fails
  at the call site with `Error: undeclared identifier: '=>'` — there is no
  `=>` operator. mapIt's parameter is already each element: use `it`
  directly (`mapIt(it * 2.0)`), or `newSeqWith(n, 300.0)` for constant
  fills.

[modules] Recursive imports fail only for some import orders (Nim 2.2.4)
  Two modules importing each other (a imports b for a type, b imports a
  for another type) compile cleanly when the entry file imports them in
  one order and fail in the other, with a misleading error pointing at a
  name:
    src/io.nim(115, 22) Error: undeclared identifier: 'PaceSegment'
    This might be caused by a recursive module dependency:
    src/integrator.nim imports src/io.nim
    src/io.nim imports src/integrator.nim
  The cycle is real, but it usually hides an *unused* import — integrator.nim
  imported io without referencing anything from it. Remove the unused
  import rather than restructuring; a cycle only survives unnoticed while
  some import order happens to resolve it, so CI must compile tests in
  every import order or the trap resurfaces later.
