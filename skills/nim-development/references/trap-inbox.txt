[build] `--styleChecks:error` is invalid — the value-taking flag is singular `--styleCheck` (Nim 2.2.4)
  Trap: the plural `--styleChecks` only accepts on/off. Passing
  `--styleChecks:error` fails before any file is read:
  `command line(1, 2) Error: 'on' or 'off' expected, but 'error' found`
  Fix: `--styleCheck:error` (singular; takes :error/:hint/:usages).
  `--styleChecks:on|off` is the legacy boolean form. (Hit while
  re-running a compile with the checker flag; cost a compile cycle.)

[nimble] a `.nimble` file named `pkg.nimble` is rejected — and the error prints a raw `$1` placeholder (nimble 0.18.2)
  Trap: the .nimble filename IS the package name, and nimble rejects
  package names ending with "pkg". Every nimble command in the project
  fails with:
  `Error: "$1" is an invalid package name: cannot end with "pkg"`
  — the unformatted `$1` placeholder looks like a nimble bug and hides
  which name offended. Fix: rename the file to the real package name
  (e.g. `mypkg.nimble`).

## [tables-index] Exported Table-typed aliases still need std/tables at the use site
- Error: `type mismatch: Expression: t[key] ... t: TomlTable, key: string`
  with only system `[]` candidates — when a module exports
  `type TomlTable* = Table[string, TomlValue]` (RRM src/io.nim) and you
  index it from another module importing only that module.
- Cause: `Table`'s `[]` comes from std/tables; the defining module's
  internal `import std/tables` is not re-exported, so the alias reaches
  you without the operator.
- Fix: `import std/tables` at the use site (RRM tools/intent_toml.nim,
  hit 2026-09-21, Nim 2.2.4).

[init] implicit `result` and `newSeq[T]` zero-fill objects — field default values are NOT applied
extends the [init] default-initialization surface (candidate, Nim 2.2.4):
two distinct zero-fill paths silently skip `field: T = value` defaults on
object types, leaving sentinel fields at 0.0 instead of the declared
sentinel.
```nim
type Ask = object
  p: float = -1.0   # sentinel: negative = absent
proc mk(): Ask =
  result.y = 5.0    # implicit result: p reads 0.0 (!)
proc mk2(): Ask = Ask(y: 5.0)  # constructor: p reads -1.0 (correct)
let s = newSeq[Ask](1)          # s[0].p reads 0.0 (!)
s[0] = Ask()                    # explicit stamp: -1.0 (correct)
```
Symptom seen: a "default-absent" flag read PRESENT everywhere, silently
zeroing every downstream value; in a simulation loop it presented as a
never-terminating run with exploding memory (state never advanced).
Fix: never rely on implicit `result` or `newSeq` for objects whose
fields carry semantic default values — assign `result = TypeName(...)`
(constructors DO apply defaults) or stamp elements explicitly after
allocation.

[init] `for x in [a, b]` iterates COPIES — mutation inside fails with "cannot be assigned to" (Nim 2.2.4)
- extends the `[init] var x zero-fills` entry's family (value semantics).
- Trap: wanting to set the same fields on two var objects, wrote
  `for st in [st1, st2]: st.params[0] = k` — arrays/seqs are value
  types, the loop variable is a copy.
- Symptom: `Error: 'st.params[0]' cannot be assigned to` at the
  assignment, not at the loop.
- Fix: assign each object directly (`st1.params[0] = k; st2.params[0] = k`),
  or iterate `for st in [addr st1, addr st2]: st[].params[0] = k`.
- Hit in unittest setup code; verified on Nim 2.2.4.
