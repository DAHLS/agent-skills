[build] `--expandMacro` prints its hint by default; silence means wrong name or template target (Nim 2.2.4)
  `nim c --expandMacro:myMacro file.nim` prints
  `file.nim(7, 13) Hint: expanded macro: 42 [ExpandMacro]` by default —
  no `--hint:ExpandMacro:on` needed; that flag's only effect is `:off`,
  which suppresses the line. SILENCE is the trap: a wrong/nonexistent
  name or a `template` target prints nothing and exits 0 — same
  silent-no-op family as `--expandArc` with a wrong target. No
  `[ExpandMacro]` hint line in the output = wrong target, not "macro
  expanded to nothing". For template semantics use a minimal runtime
  probe (`nim c -r`).
  (Corrected resubmission of the rejected "silent by default" entry; all
  claims verified in the round-2 audit, runs A1-A5.)

[idiom] `block` is a Nim keyword — illegal as a parameter name (Nim 2.2.4)
Trap: naming a proc parameter `block` (e.g. a JSON block) fails to compile.
Symptom: `Error: expected closing ')'` pointing at the parameter line —
misleadingly a *syntax* error, not a "keyword in use" error.
Fix: rename the parameter (e.g. `riderBlock`); keywords like `block`,
`type`, `addr`, `mixin` cannot be parameter names.
```nim
proc merge(b: JsonNode) = discard     # fine
proc merge(block: JsonNode) = discard # Error: expected closing ')'
```

[build] `nim c -o bin/rrm` fails — the output flag needs the colon form (Nim 2.2.4)
  Trap: passing the output binary as a separate token.
  Symptom: `Error: argument for command line option expected: '-o'`
  Fix: `nim c -o:bin/rrm src/rrm.nim` (colon-attached value).

[nimble] `nimble test` refuses a nimble file with an empty license field (nimble 0.14.x)
  Trap: project `.nimble` written with `license = ""` (stdlib-only repo, no
  license chosen yet).
  Symptom: `Error: Incorrect .nimble file: ... does not contain a license field.`
  Fix: run the test binaries directly (`nim c -r tests/tfoo.nim`) or set a
  license string; the task's exec lines are otherwise fine.

[float] extends the [float] bitwise-== entry: a decimal literal pin of a
  float product is one rounding off (Nim 2.x)
  Trap: pinning `check x == 46.8` where x is computed as `0.78 * 60.0`.
  0.78 has no exact binary form, and the correctly-rounded product
  0.78 * 60.0 == 46.800000000000004 != 46.8 (the nearest double to the
  decimal). Meanwhile 0.78 * 90.0 == 70.2 exactly — the literal pin
  passes or fails per-constant by accident of the roundings.
  Symptom: unittest `Check failed: x == 46.8` with the diff in the 12th
  digit, only for some constants in the same suite.
  Fix: pin the product expression itself (`check x == 0.78 * 60.0`) so
  both sides take the same rounding, or probe the exact repr before
  freezing a literal pin. Verified by /tmp probe 2026-09-15.

[init] `var x: T` zero-fills — object field default values apply ONLY in T() constructions
trap: declaring `var st: MyObj` where MyObj has `field*: float = 36.8` gives 0.0,
  not 36.8. Field defaults are construction-time (T(), result of procs returning T),
  never declaration-time.
symptom: assertion like `var st: PhysiologyState; st.coreC == 36.8` fails with 0.0.
fix: use `var st = MyObj()` (or the constructing proc) when defaults are meant:
  var st = PhysiologyState()   # 36.8
  var st2: PhysiologyState     # 0.0 — zero-init, defaults ignored
(Nim 2.2.4, verified by minimal probe.)

[ambiguity] identifiers differing only in case after the first char are the SAME symbol
trap: `let dt = ...` followed by `let dT = ...` in the same scope — Nim's
  style-insensitive ident matching (first char case-sensitive, rest ignored) makes
  them one symbol.
symptom: "Error: redefinition of 'dT'; previous declaration is here" even though
  the spellings differ.
fix: rename one (e.g. `dT` -> `dTemp`); no compiler flag disables this —
  --styleChecks only governs style warnings, not symbol identity.
(Nim 2.2.4.)

[json] `%*` as a bare call argument parses the trailing `{...}` as an extra macro argument (Nim 2.2.4)
`seq.add %* {...}` — a multi-line table constructor after the `%*` macro,
without parentheses — fails to compile with a confusing overload error:
  Error: type mismatch ... [2] macro `%*`(x: untyped): untyped
    extra argument given
The parser splits `%*` and `{...}` into two arguments of `add`/the macro
resolves them as separate params. Fix: parenthesize the whole macro call —
  riders.add(%*{"rider": i + 1, "steps": r.steps,
     "max_core_c": r.maxCoreC})
Single-line `x.add %*{"a": 1}` is fine; it bites when the table is broken
across lines.

[footgun] Positional args silently bind to DEFAULTED params — no warning, wrong physics (Nim 2.2.4)
CANDIDATE (extends the general overload-mismatch entry; promote beside it if verified)
Trap: calling a proc that has default parameters (`proc advance*(st, params, deliveredW, dt,
glycogenScale = 1.0, vApp = 12.0, tempC = 20.0, rh = 0.5)`) with extra POSITIONAL
arguments binds them left-to-right into the defaults' slots — passing
`advance(st, p, 304.0, 1.0, 1.0, 8.2, 0.30)` sets vApp = 8.2, tempC = 0.30, not the
intended tempC = 8.2, rh = 0.30.
Symptom: no compile error, no hint; the call runs with silently different operating
context. Observed 2026-09-17: unit tests computed targets at ambient 0.3 °C and PASSED
by coincidence against a wrong operating point until an unrelated grid check exposed
negative E_req where positive was asserted.
Fix: after any defaulted param, use NAMED arguments for the rest of the call:
`advance(st, p, 304.0, 1.0, vApp = 12.79, tempC = 8.2, rh = 0.30)` — or always name
optional-position args in tests that pin numeric operating points.
