[modules] Top-level routine used before its declaration → undeclared identifier
Trap: at module scope Nim resolves symbols top-down — calling proc B from
proc A's body fails with `Error: undeclared identifier: 'B'` when B's
`proc` is written below A in the file (true even for plain non-generic
procs; there is no implicit forward referencing).
Symptom: `undeclared identifier: 'eventName'` / `'PostureClass'` at the
call site, though the symbol exists later in the same module.
Fix: move the callee above every caller (or add a forward declaration
`proc foo*(x: T): R {.forward.}` — reordering is the idiomatic fix).
Snippet:
  proc eventName*(k: EventKind): string = ...   # must come FIRST
  proc eventToJson*(e: Event): JsonNode =
    result["kind"] = %(eventName(e.kind))       # now resolves
(Nim 2.2.4, observed 2026-10-01.)

[idiom] `@[]` literals in a call to an openArray[T]/typed param → type
mismatch "seq[empty]"
Trap: passing bare `@[]` for a `seq[WindLineSlot]`/typed parameter makes
the literal infer `seq[empty]` and the call fails with
`Error: type mismatch ... [1] @[]: seq[empty]` (the element type cannot
propagate INTO the literal from an overloaded proc's params).
Symptom: the "Expected one of" block lists the right overload with the
literal slot mismatched at its position.
Fix: bind an explicitly-typed empty first (`var wsl: seq[WindLineSlot]`
then pass `wsl`), or write `@[].seq[WindLineSlot]`.
(Nim 2.2.4, observed 2026-10-01; test-side call, one compile cycle.)

[proc-const-array] A `const` array literal inside a proc that references a
PROC PARAMETER fails with: `Error: cannot evaluate at compile time:
distKm`. Seen on Nim 2.2.4 building a fixture Route:
`const w = [WeatherPoint(distKm: distKm, ...)]` inside
`proc flatRoute(distKm: float)` — the literal looks static but binds the
runtime param. Fix: `let w = [...]` (or hoist the constant out). Cousin of
the implicit-result/no-defaults class: anything spelled `const` is a
compile-time demand on every referenced name.

[orc] `defer` in a proc returning a string-keyed `Table` corrupts the
returned keys (Nim 2.2.4, --mm:orc default)
Trap: a proc that builds a `Table[string, TomlValue]` (via repeated
`t[k] = v` from parsed line slices) and also carries `defer:
removeFile(path)` returns a table whose key strings are garbage on
lookup — `in`/`[]` miss keys that echo back with trailing bytes
(`KEY:pull_shape .`, `KEY:food_cho_g e_min.`), duplicated entries, and
dependent `both keys required` logic misfires. Silent: no crash, no
error; lookups just fail.
Symptom: the SAME parse call passes at top level / in a defer-free
proc / under `--mm:refc`, and fails only in the defer-carrying proc
under orc/arc. Import-set sensitive (inlining changes whether the
buggy destructor ordering fires).
Fix: drop the `defer` from the table-building proc (do cleanup at the
call site, or reuse one overwritten temp file), or return a copy built
after the defer scope. Verified minimal: removing the single `defer`
line flips the run from corrupted keys to clean (orc); arc also
corrupts, refc clean.
(Nim 2.2.4, observed 2026-10-03; unit-test helper, ~1 h of diagnosis.)

[types] Heterogeneous array branches + `array & array` both fail where seqs work (Nim 2.2.4)
Candidate added 2026-10-04 by a subagent session (RRM collections-seam).

Two related type-mismatch traps in one session, both against exported
`const ... = ["a", "b"]` arrays from a library:

1. `let allow = if kind == "r": riderMetaKeys else: routeMetaKeys`
   where both consts are `const x = [...]` arrays of DIFFERENT lengths
   (`array[0..6, string]` vs `array[0..3, string]`) ->
   `Error: type mismatch: got 'array[0..3, string]' for 'routeMetaKeys'
   but expected 'array[0..6, string]'`. An if-expression needs ONE
   result type; fixed-length arrays of different sizes don't unify.
   Fix: annotate as seq — `let allow: seq[string] = if ...: @riderMetaKeys
   else: @routeMetaKeys`.

2. `riderTunableKeys & physiologyKeys` where both are const arrays
   (`array[0..4, string] & array[0..5, string]`) -> type mismatch against
   every `&` overload. The `&` that joins collections is seq-only.
   Fix: `var s: seq[string] = @riderTunableKeys; s.add physiologyKeys`.

Lesson: treat exported `const [...]` arrays as read-only iteration
surfaces; the moment you branch on them or concatenate them, convert to
seq with `@` explicitly (or type the target `seq[string]`).

[exn] `except A, B as e:` does not compile — bind a name per type (Nim 2.2.12)
  A multi-type except clause cannot attach ONE `as e` binding after a
  type list:
    except IOError, OSError as e:   # Error: undeclared identifier: 'as'
  Fix: bind per type (`except IOError as e, OSError as e:`), or drop the
  binding and use getCurrentExceptionMsg():
    except IOError, OSError:
      stderr.writeLine getCurrentExceptionMsg()

[os] `copyFileWithPermission` does not exist — it is `copyFileWithPermissions` (or plain `copyFile`) (Nim 2.2.12)
  Symptom: tests/test_x.nim(37, 5) Error: undeclared identifier:
  'copyFileWithPermission'
  std/os exports `copyFileWithPermissions` (plural — src, dest, options)
  and `copyFile` (src, dest). Singular-s spelling is a compile error.

[build] Stale nimcache links with "undefined reference"/"hidden symbol isn't defined" after src or compiler updates (Nim 2.2.12)
  Symptom: `nim c -r tests/foo.nim` compiles every module but the final
  gcc link fails:
    /usr/bin/ld.bfd: @mfoo.nim.c:(.text+0x3819): undefined reference to `eqdestroy___OOZsrcZio_u19121'
    /usr/bin/ld.bfd: hidden symbol `eqsink___OOZsrcZio_u999' isn't defined
    final link failed: bad value
  Cause: ~/.cache/nim/<exeName>_d still holds .o files generated against
  a different version of an imported module (here src/io.nim changed
  upstream; the per-exe default cache dir is keyed by OUTPUT name, so a
  test not rebuilt since the change has a fully stale cache).
  Fix: rm -rf ~/.cache/nim/<exeName>_d (or all of them) and rebuild —
  not a code error; do not chase the missing symbols in source.

[idiom] `lent T` is invalid as a proc PARAMETER type — return-position only (Nim 2.2.4)
Trap: trying to borrow a large object argument with `proc f(x: lent T): R`
fails to compile; `lent` exists for return types and cursor-ish bindings,
never in a parameter list. Even `--experimental:views` doesn't enable it.
Symptom: `Error: invalid type: 'lent T' in this context: 'proc (x: lent T): R' for proc`
Fix: under ORC/ARC a never-mutated object param with hooks (seq fields) is
already passed as a pointer in the generated C with no call-site copy —
leave the plain `T` param and instead remove the real copies: closure
captures of the param (each capture = a full deep copy per call; restructure
the nested proc to take it as a parameter) and whole-value `let y = obj.field`
copies (use `let y {.cursor.} = obj.field` or indexed reads). Verified in
generated C: callers pass their own `tyObject_X*` param slot straight
through, zero `eqcopy` calls.
```nim
proc f(x: BigObj): R =          # NOT `lent BigObj`
  proc helper(x: BigObj; i: int): float = x.data[i]  # no capture = no env copy
  helper(x, 3)                   # pointer pass, no copy
```
