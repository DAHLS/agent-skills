[footgun] `var obj: Obj` zero-fills every float field — default-constructed
  records read as real data in diff/baseline assertions.
  Trap: Nim object default initialization gives 0.0 for all float fields
  (and 0 for ints/enums). A test that constructs a params record with only
  the interesting field set, then diffs ALL fields against nonzero
  baselines, silently reports every unset field as a "deviation".
  Symptom (unittest): `Check failed: log.len == 1` — `log.len was 8`;
  the record's mass_kg 0.0, sample_step_m 0.0 etc. all differed from
  their 61.0/10.0 baselines.
  Fix: in tests, set every diffed field to its baseline explicitly (or
  init from a baseline constructor) before overriding one field:
    proc baseline(): Params = Params(massKg: 61.0, sampleStepM: 10.0, ...)
    var p = baseline()
    p.crr = 0.0035

[footgun] `1.0 - x` rounds to exactly 1.0 once x < machine epsilon near 1.0
  Trap: asserting `1.0 - k*exp(-t) < 1.0` (asymptote "never attained") on
  float64 — the subtraction is exact-bound by eps(1.0) ≈ 2.22e-16, so any
  subtrahend below ~1e-16 vanishes and the expression evaluates to EXACTLY
  1.0 (observed: k=0.214, t≈430 → exp underflow → result 1.0, strict
  `check f(g) < 1.0` failed with literal "was 1.0").
  Symptom: a mathematically strict inequality silently becomes equality for
  extreme inputs; unit test passes at sane inputs, fails at extreme ones.
  Fix: anchor strict inequality assertions in the physically meaningful
  regime (input magnitudes the spec covers), or compare `k*exp(-t) > 0.0`
  instead of `1.0 - k*exp(-t) < 1.0`.

[footgun] unittest `fail()` bumps the global failure count WITHOUT marking
  the current test FAILED — suite prints all [OK] but exits 1.
  Trap: a test helper (typically an expect-error helper) calls `fail()` on
  the unexpected-accept path inside `try/except`; if the expected exception
  stops being raised (e.g. you lifted a not-implemented boundary),
  std/unittest's `fail()` increments the process failure counter but does
  not set the current test's status, so the label still stamps [OK].
  Symptom: run prints e.g. 84 `  [OK]` lines, zero `[FAILED]`/`Check
  failed` lines, yet the binary exits 1 (`nim c -r` then reports "Error:
  execution of an external program failed" with no visible cause).
  Fix: never gate an expect-error helper on `fail()` alone — make the
  accept path a hard `check` with a message, or assert the positive
  contract when a boundary is lifted:
    try:
      discard load(path)
      check false  # prints "Check failed" with the file:line
    except SchemaError as e:
      check e.msg.contains(needle)

[idiom] Export marks are illegal on named-tuple fields (Nim 2.2.4)
Trap: writing `FieldSample* = tuple[tS*: float, order*: seq[int]]` in a
type section — the `*` after a tuple FIELD is not grammar.
Symptom: compiler error at the first starred field, e.g.
  `Error: ':' or '=' expected, but got '*'` (pointing at the `tS*:` line,
  confusingly far from the tuple declaration line).
Fix: star only the type name; fields stay bare:
  `FieldSample* = tuple[tS: float, order: seq[int]]` — field access from
  other modules works anyway because the TYPE is exported, not fields
  (tuples have no visibility of their own). Object fields, in contrast,
  DO need per-field `*`.
